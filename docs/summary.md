# 백엔드 패키지 리팩토링 핵심 요약 (팀원 공유용)

이번 리팩토링은 복잡했던 백엔드 도메인을 **Foundation(기반), Core(핵심), Support(지원)** 3개의 큰 계층으로 정리하고, 서로 엉켜있던 의존성을 깔끔하게 끊어내는 작업이었습니다.

---

## 🚨 핵심 변경 사항 및 행동 지침

### 1. (백엔드) 대규모 패키지 이동에 따른 import 에러 대처

기존 클래스들의 패키지 경로(`com.sparta.spartatigers.domain.~`)가 대대적으로 변경되었습니다.

- `git pull` 이후 무수히 많은 에러가 뜬다면 당황하지 마세요.
- IDE(IntelliJ, VS Code)의 **자동 import 갱신 기능**(`Optimize Imports` 등)을 활용해 꼬인 경로를 다시 잡아주세요.
- 에디터 캐시 문제가 발생할 경우 `./gradlew clean build` 또는 에디터 캐시 초기화를 진행해 주시면 됩니다.

### 2. (백엔드) ⚠️ 엄격한 패키지 의존성 룰 적용 (Zero Magic)

앞으로 코드를 작성하실 때 아래 규칙을 어기면 **자동화된 ArchUnit 테스트(`ArchitectureTest.java`)가 실패하여 전체 빌드가 중단**됩니다.

- **역방향 참조 금지:** `Core`(비즈니스 로직)나 `Support`(인프라)는 `Foundation`(기본 엔티티)을 호출할 수 있지만, 반대로 `Foundation` 계층에서는 절대 위를 쳐다보면 안 됩니다.
- **Core 간의 직접 참조 금지:** 이게 가장 중요합니다.
  - 예를 들어 `trade`(거래) 도메인의 Service에서 `direct`(채팅방) 도메인의 Service를 `@Autowired`로 직접 가져다 쓰면 안 됩니다.
  - **👉 대안:** 한 도메인의 로직이 끝난 후 다른 도메인의 동작이 필요하다면, **Spring Event(`ApplicationEventPublisher`)를 통해 이벤트를 발행**하고, 상대방이 이를 구독(Listener)하는 방식으로 느슨하게 연결해야 합니다.

### 3. (프론트엔드) 📢 라이브보드 API 데이터 분리

백엔드 도메인 분리 원칙(비즈니스 도메인이 날씨와 같은 외부 인프라 도메인을 직접 참조 금지)에 따라, 기존에 하나의 API로 내려주던 데이터가 쪼개졌습니다.

- **변경 전:** 라이브보드 방 입장 시 날씨 정보(ForeCast, NowCast)까지 한 번에 내려줌
- **변경 후:** 라이브보드 DTO 내부에서 날씨 관련 필드 전체 삭제
- **👉 프론트엔드 액션 아이템:**
  앞으로는 아래 **2개의 API를 병렬(`Promise.all` 등)로 각각 호출**한 뒤, 프론트엔드 상태(State)에서 직접 조합하여 화면을 그려주셔야 합니다.
  1. `GET /api/liveboard/room/{id}`
  2. `GET /api/weather/{stadiumId}`
